# Satellites

A satellite is the thing that actually runs the agent. Elysium is its control plane and
nothing more: Elysium decides what should happen and to whom it is visible, and a satellite
decides how it happens and does it.

The contract is defined in
[arsox-satellites](https://github.com/JalapenoLabs/arsox-satellites) and that repository's
README is the authority. This document covers what Elysium needs from it and how Elysium
models it.

**Arsox keeps its name.** Elysium is the workspace; Arsox is the execution plane it drives.

## What the contract gives Elysium

- **Protobuf in both directions**, over ordinary HTTP plus a unidirectional WebSocket for
  events. A JSON rendering exists for hand-driven debugging only.
- **`ARSOX_SECRET` is a bearer token** the caller presents. The satellite fails to start
  without it. It never reaches an agent's environment, and it must never reach a browser.
- **Threads are the unit of conversation.** IDs are UUIDv7 generated by the satellite, never
  by the client, because they become filesystem paths. A thread holds a workspace, cloned
  repositories, prefetched issues, and an assembled `AGENTS.md`.
- **One turn at a time per thread, strictly FIFO.** Turns queue rather than run in parallel.
  Threads run concurrently with each other up to `ARSOX_MAX_CONCURRENT_THREADS`.
- **Any process holding the URL, the secret, and the thread id can attach.** No lease and no
  ownership, which is what makes a horizontally scaled Elysium possible. Persist the thread
  id and any replica picks the work back up.
- **Every event carries a monotonic `sequence` and is persisted before it is sent.**
  Reconnect with `?from_sequence=<n>` and a network blip costs nothing. A consumer that lags
  is closed loudly with `STREAM_CONSUMER_LAGGED` rather than starved quietly.
- **Budgets are required at thread creation**, with an explicit unlimited value if that is
  genuinely intended. Enforcement is by an LLM proxy that counts tokens, not by prompt.
- **Permissions are deterministic and enforced by the satellite.** An egress proxy, an exec
  allowlist brokered through a shim directory the agent cannot write, a root-owned pre-push
  hook, filesystem scoping, and secret redaction. Instructions in `AGENTS.md` are advisory
  and always will be.
- **Nothing fails silently.** Every failure at every severity is an **incident** with a
  stable code and a disposition (`fatal`, `recovered`, `degraded`, `blocked`), emitted on the
  stream and queryable afterward. Incidents outlive their thread.
- **Errors are one shape everywhere**: a stable enum code, a message, a `retryable` flag, and
  structured details. Match on the code, never on the message, and fall back to `retryable`
  for codes a client has never heard of.

## The Rust SDK

`arsox-sdk` is the client Elysium calls. It ships the generated contract unconditionally and
the HTTP and WebSocket client behind a default-on `client` feature.

- `Satellite::connect(url, secret)` checks `/v1/version` and refuses a satellite serving a
  higher proto major, rather than letting the mismatch surface as a decode failure three
  calls later. A higher minor warns once and proceeds.
- `version()`, `status()`, `harness()`, and `incidents(query)` on the satellite.
- `threads()` gives `create`, `create_with` (idempotency key plus correlation metadata),
  `attach`, `list`, and `list_ordered`.
- A `ThreadHandle` gives `get`, `start_turn`, `start_turn_with`, `turns`, `incidents`,
  `destroy`, `events`, and `events_from(sequence)`.
- **Stopping a thread is three verbs**: `pause` stops claiming work and keeps the backlog,
  `resume` starts again, and `drain` clears what is queued and returns the ids it cancelled.
  They compose, so the caller says which they meant.
- A `TurnHandle` gives `id`, `queued`, and `result`.
- One `Error` type answers three questions: `code()`, `is_retryable()` (read from the
  satellite's own flag, which is what makes an older SDK safe against a newer satellite), and
  `is_not_found()` / `is_incompatible()`.

**A handle is not a thread.** Every piece of state lives on the satellite, which is what
makes handles disposable and threads durable.

`GET /v1/harness` is the interesting endpoint. A harness might have no plan mode or no
sub-agents, and a UI that offers a control the harness cannot honor is worse than one that
hides it. Capability reporting exists so the interface can ask up front instead of inferring
from silence three turns in.

## Current state

The contract, the satellite image, and the Rust, Node, and Python SDKs all exist on that
repository's `develop` branch. The image is not published to a registry yet, so it is built
from a clone:

```sh
git clone --branch develop https://github.com/JalapenoLabs/arsox-satellites.git
cd arsox-satellites && docker build --tag arsox-satellite:dev .
```

Elysium pins the SDK to an exact revision, the same discipline the Anubis pins follow, and
pins the image tag alongside it. SDK major versions track proto major versions, so the image
tag and the SDK version move together.

Not in the SDK yet, and therefore not reachable from Elysium: artifacts, suggestions, plan
approval, question answering, streaming settings toggles, and the control socket. The SDK
grows to match as the satellite does.

## What Elysium will model

Proposed, not built. **Blocked on the project tier ([tenancy.md](tenancy.md),
[Anubis #93](https://github.com/JalapenoLabs/Anubis/issues/93))**, because a Satellite belongs
to a Project and Project has no home in the framework yet.

| Model | Owner | Holds |
|---|---|---|
| `Satellite` | `Project` | Name, base URL, sealed bearer secret, last-seen health, reported version and proto major, reported harness capabilities |
| `Thread` | `Satellite` | The satellite's thread id, title, state, idle TTL, budgets as created, the creating membership, and the highest mirrored sequence |
| `Turn` | `Thread` | The satellite's turn id, prompt, status, the submitting membership, and token and cost totals |
| `ThreadEvent` | `Thread` | Sequence, type, and payload, as mirrored from the socket |
| `Incident` | `Thread` | Code, disposition, retryable, message, details, occurred-at |

Ownership chains to a tenant in every case, which is what makes the framework's guards do the
tenancy work. Nothing is owned by a user directly.

`ThreadEvent` and `Incident` are hand-written and read-only rather than scaffolded. They are
append-only mirror tables written by the stream reader, so the create, update, and destroy
handlers and the form a scaffold produces would all be waste.

Two things deliberately do **not** get a model:

- **Artifacts** are listed and downloaded from the satellite on demand. Mirroring a 100 MiB
  artifact into Postgres to avoid one proxied request is the wrong trade.
- **Workspace files** are the satellite's, always. Elysium lists them through the satellite
  and never caches a tree that changes under it.

### Why the secret is a column and not a settings blob

A satellite's bearer secret is the one credential that grants total authority over that
satellite, so it is sealed with `anubis::auth::secret_box` and stored in its own column,
never inside a JSON settings document. A typed column is greppable and a reviewer can see
every place it is read; a key inside a blob is not, and the fourteenth credential added to
that blob is the one that leaks. The satellite contract makes the same call with
`common.v1.Secret`, for the same reason.

The secret is never returned to a client. Responses carry a redacted display string.

## Registration, and the reachability question

Elysium is the client and the satellite is the server: Elysium dials out to a base URL and
presents the secret as a bearer token. Registering therefore means giving Elysium an address
and a secret, and Elysium confirming it by calling version and harness before saving the
record, so a typo fails at the form rather than at the first job.

That works when the satellite is reachable from wherever Elysium runs: a self-hosted runner
with a routable address, a machine on the same private network, or a home machine behind a
tunnel such as Tailscale or Cloudflare Tunnel. **The common self-hosted case, Elysium and its
satellites on one LAN, works with no tunnel at all.**

It does not work for a satellite behind NAT that Elysium cannot reach. The alternative is
inverting the connection, with the satellite dialing out and Elysium multiplexing commands
back down it. That is a satellite-side protocol change, not an Elysium feature, and it needs
to be designed in `arsox-satellites` rather than assumed here. Until then, "bring your own
tunnel" is the documented answer and the registration UI should say so honestly rather than
let a user discover it when their satellite never connects.

## Mirroring

For each satellite a project owns, Elysium holds one WebSocket per active thread and records
the highest sequence it has stored. Reconnection replays from `from_sequence + 1`, so a
network blip costs nothing and a restarted Elysium catches up rather than losing history.

Two failure modes come straight from the contract and both need handling on day one:

- **`STREAM_CONSUMER_LAGGED`**: Elysium fell behind and was closed. Reconnect from the last
  stored sequence. Degrading loudly is the contract working as intended.
- **`STREAM_SEQUENCE_EXPIRED`**: the requested sequence is older than the satellite's
  retained history. The mirror has a hole in it, and the honest response is to mark the gap,
  not to renumber around it and present a stream that looks complete.

Statistics events are not emitted over the socket by default because they change rapidly.
Elysium fetches usage on demand rather than opting in.

## The live thread view

Where the work is watched, and the flagship Elysia panel
([workspace.md](workspace.md)). The event stream renders agent messages, tool calls, team
chat, direct messages between members, integration requests and their outcomes, checker
results, and service logs, in sequence order.

Three things make it more than a log:

- **Questions.** The commander asks between one and five at a time, each with up to five
  options, answered as a set. Two people may be looking at the same thread, so the interface
  has to handle losing the race: `QUESTION_SET_ALREADY_ANSWERED` means someone else answered,
  and the right response is to show what they said, not to retry.
- **Plans.** Same shape, same race, `PLAN_ALREADY_DECIDED`.
- **Incidents.** Inline, at the point in the stream where they happened, colored by
  disposition. `blocked` reads as the permission system working. `recovered` reads as a
  warning, because a failover nobody sees is a bill nobody explains.

Team mode changes the view rather than the model: members are lanes, and the commander's view
is the conversation between them rather than every tool call any of them made.

## Budgets, permissions, and who may raise them

Budgets are required at thread creation, with an explicit unlimited value if that is
genuinely what is meant. Elysium surfaces this as a required field and never defaults it
silently, because the whole point of the contract's choice between a value and an `Unlimited`
message is that an unbounded spend is a decision somebody made.

Which member may register a satellite, start a turn, answer a question, approve a plan, or set
an unlimited budget is expressed in `config/roles.yml` and nowhere else.

Permissions passed to a satellite are settings Elysium stores and forwards. **Elysium does not
enforce them and must never present itself as if it does.** Enforcement is the satellite's, by
infrastructure the agent cannot reach. An Elysium UI that implies otherwise is lying about the
security model.

## The one rule about incidents

The satellite records every failure at every severity as an incident, including the ones that
recovered on their own, and the contract states plainly that a code path which swallows a
failure is a bug. Elysium mirrors that rule: an incident that arrives on the stream is stored
and shown. Elysium does not filter incidents on the way in, because a control plane that
hides failures is worse than one that has none to show.

`recovered` incidents in particular are the ones worth surfacing rather than hiding. A
failover that works looks exactly like success, and it is being paid for on every call.

## Build order

Each step is useful on its own, and each depends on the one above it. Step 1 is blocked on the
project tier.

1. **Satellite registration**, with the reachability probe at the form.
2. **Thread creation and the turn queue.**
3. **The live thread view**, which is the first thing that feels like the product.
4. **Questions and plans**, which is the first thing that makes it usable unattended.
5. **Artifacts, usage, and incidents.**
6. **Team mode**, a view change over an event stream that already carries it.
