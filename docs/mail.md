# Mail

Elysium hosts a **full mail server per project** — send and receive on the project's
domain(s) — as a managed integration (`docs/integrations.md`). Mail is a **project**
resource (`docs/projects.md`): the org is the umbrella, the project owns the domain and the
mail server. This is the first real feed into the "bring things TO you" action-center.

## Architecture: MTA edge + Elysium owns the mailbox (model B)

The container is a **pure MTA edge**; **Elysium owns the canonical mailbox.** Unlike a
storage Drive (an external source of truth we never mirror), our mail server *is* part of
Elysium, so Elysium owning the mail is authoritative, not duplication.

- **Inbound:** the edge accepts SMTP on port 25, filters spam and verifies DKIM/SPF/DMARC at
  the boundary, then **delivers each accepted message into Elysium via LMTP.** Elysium
  stores, indexes, threads, and fires the realtime event. The edge never holds mail
  long-term.
- **Outbound:** the action-center composes/replies → Elysium submits to the edge → **Rspamd
  DKIM-signs** → the edge delivers **direct or via a smarthost relay**.
- **The action-center is the mail client.** Mail is first-class unified data, searchable
  alongside files/repos/people, realtime over the SSE bus, resolved (not merely read) as
  action items.

External IMAP/POP retrieval (using a third-party mail app against an Elysium mailbox) is
**deferred**; Elysium is the client and reads its own store.

## Blessed image: Postfix + Rspamd

A lean edge, pluggable, config generated by Elysium (never hand-edited by the operator).

- **Postfix** — the reference MTA: inbound 25, LMTP handoff to Elysium, outbound relay
  (direct or smarthost), transport/virtual maps, per-domain routing.
- **Rspamd** — spam scoring, **DKIM signing (out) + verification (in)**, and DMARC.
- **Spam runs at the edge, during the SMTP transaction:** obvious junk is *rejected* (5xx)
  before acceptance, so we neither take responsibility for mail we'd trash nor pollute the
  store. Borderline mail is accepted, scored, and delivered with its score for configurable
  foldering in the action-center.
- Alternative (only if the deferred external-IMAP nicety becomes a priority): an all-in-one
  like Stalwart — at the cost of overlapping model B's storage.

## Port 25: one shared SMTP router, many project containers

The host has exactly one port 25. Inbound mail is routed by the **domain's MX record**, and
a single **shared SMTP router owns port 25**, reading the envelope recipient (`RCPT TO:`)
and forwarding to the **owning project's edge container.** Routing is by **recipient
domain, not TLS SNI** (port-25 SMTP starts plaintext, upgrading via STARTTLS only after the
recipient is known — so the M2 HTTP/SNI router does not apply). Many projects → many edge
containers → one shared router → one shared control plane.

## Address & mailbox model

- **Per-project auto-provision policy, default ON.** A project with auto-provision on gives
  every project member an address on its domain (a company domain: everyone gets one). A
  product/vanity domain can turn it off and assign addresses explicitly (`support@`,
  `hello@`, a few people) so it does not mint dozens of unused mailboxes.
- **Local parts** derive from the user (e.g. `given.family` or a chosen handle), unique per
  domain, collision-handled, and editable.
- **Aliases & distribution addresses.** A mailbox may have several addresses; an alias may
  fan out to several mailboxes (a role/distribution address like `support@` → the support
  team).
- **Mandatory catch-all.** Every domain has a catch-all for unknown local parts, delivering
  to a configurable destination — **the project owner by default.** (Tradeoff: a catch-all
  also receives spam to made-up addresses, so the catch-all inbox is filterable.)
- **Multiple domains per project** are supported; the mail server multi-homes them.

## Storage: capacity = your Drive, no artificial quota

- **Message bodies/attachments → an `OBJECT_STORE` Drive**, project-scoped, bound explicitly
  at provision time (picker defaults to the project's default Drive). Bodies are large and
  mostly immutable — an object-store fit.
- **Metadata / threading / flags / search index / a preview snippet → Postgres.** Small,
  relational, ACID; keeps list/search/inbox instant while bodies lazy-load from the Drive.
- **Edge spool → an ephemeral local volume** (a transient queue, nothing precious).

Because bodies live on the bound Drive, a mailbox is only "full" when *your storage* is —
bring a 2 TB bucket and there is no 30 GB ceiling. **Quotas are optional admin policy, never
a platform limit** (off by default; an admin may set soft per-user/project quotas for
fairness).

## DNS & deliverability: the responsibility split

Provisioning the container is the easy part; DNS + reachability + IP reputation decide
whether mail actually flows.

- **Elysium owns and automates:** generates all required DNS records (`MX`, `SPF`, the
  `DKIM` public key, `DMARC`) copy-paste ready; **generates and seals the DKIM keypair**
  (`crypto.rs`) and provisions the private key into the edge; **continuously verifies**
  records with live lookups (green/red); and runs a **deliverability diagnostics panel**
  (inbound 25 reachable? outbound 25 open? PTR match? IP on a blocklist?).
- **The operator owns** (consistent with "SSL/hosting is your responsibility"): setting the
  DNS records, port-25 reachability, a static IP, and requesting PTR. Optional later:
  DNS-provider API integration (Cloudflare/Route53) to auto-write records.
- **Outbound supports a smarthost relay as a first-class option.** Because direct outbound
  from a home/cloud IP frequently fails (blocked 25, cold reputation), a project can relay
  outbound through SES/Postmark/Mailgun/SendGrid/an ISP relay while still receiving
  directly. Relay is the reliable default; direct-send is available for a proper static
  IP + PTR + reputation. This is also what makes the magic-link sign-in reliably
  deliverable.

## Identity

- **v1:** the action-center ↔ Elysium ↔ edge path is **internal trust** on the isolated
  network — Elysium is the client and the user is already signed into Elysium. No separate
  mail login.
- **Deferred (with external clients / IMAP):** third-party client auth (SMTP-AUTH / IMAP)
  via **Elysium-minted app-passwords** (the M3 credential-minting layer), the way Google/
  Microsoft issue app-specific passwords.

## Roadmap dependencies

- Outbound mail unblocks **passwordless email sign-in** (magic link / OTP), designed in
  `docs/auth-model.md` and gated on outbound existing.
- Mail is a project-scoped managed integration; it depends on the storage foundation
  (`docs/storage.md`), the orchestration control plane and per-project provisioning
  (`docs/integrations.md`), and the identity/SSO spine.
